
Lista de prioridades

Alta

Persistência: Migrar dados para MongoDB (ou SQLite) e configurar conexões.
Segurança: Hash de senhas (bcrypt) e armazenamento seguro.

Média

Cancelamento: Implementar regras de cancelamento e endpoint correspondente.
Admin CRUD: CRUD de serviços e funcionários no painel admin.
Validação: Validar entradas (express-validator/Joi) e tratar erros com HTTP codes.

Baixa

Templates: Padronizar layout/partials (views), limpar duplicação HTML.
Testes & Docs: Escrever testes básicos e README.md.


2. Usuários do sistema

O sistema terá três tipos de usuário:

Cliente

Pode:

- Criar uma conta.
- Fazer login.
- Visualizar os serviços disponíveis.
- Escolher um profissional.
- Consultar horários disponíveis.
- Realizar um agendamento.
- Visualizar seus próximos agendamentos.
- Cancelar um agendamento dentro das regras definidas.
- Consultar seu histórico de agendamentos.

Funcionário

Pode:

- Visualizar sua agenda.
- Consultar os agendamentos do dia.
- Confirmar um atendimento.
- Marcar um atendimento como concluído.
- Cancelar ou remarcar um atendimento.
- Bloquear determinados horários

Administrador

Pode:

- Cadastrar, editar e remover serviços.
- Cadastrar funcionários.
- Definir horários de trabalho.
- Definir dias de funcionamento.
- Gerenciar clientes.
- Visualizar todos os agendamentos.
- Criar, editar e cancelar agendamentos manualmente.
- Bloquear horários.
- Visualizar estatísticas básicas.

3. Fluxo principal do cliente

O cliente acessa o site e seleciona:

Serviço → Profissional → Data → Horário

Por exemplo:

«Corte masculino
João
15/08/2026
14:30»

Depois disso, o sistema apresenta um resumo:

«Corte masculino
João
15/08/2026 às 14:30
Duração: 45 minutos
Valor: R$ 40,00»

O cliente confirma o agendamento.

O sistema registra o agendamento e apresenta uma confirmação.

4. Regras de negócio

O sistema deve impedir que dois clientes ocupem o mesmo horário.

Também deve considerar:

- duração do serviço;
- horário de funcionamento;
- intervalo entre atendimentos, quando aplicável;
- folgas do funcionário;
- horários previamente bloqueados;
- agendamentos existentes;
- antecedência mínima para agendamento;
- prazo mínimo para cancelamento.

Exemplo

Se João trabalha das 08:00 às 18:00 e um corte dura 45 minutos, o sistema não deve oferecer horários que ultrapassem o horário de encerramento.

5. Painel administrativo

O administrador terá um dashboard contendo:

- Agendamentos de hoje.
- Agendamentos futuros.
- Atendimentos concluídos.
- Cancelamentos.
- Quantidade de clientes.
- Serviços mais agendados.

Também deverá existir uma visualização de agenda.

Exemplo:

Horário| Profissional| Cliente| Serviço| Status
09:00| João| Carlos| Corte| Confirmado
10:00| João| Pedro| Barba| Concluído
11:00| Maria| Ana| Corte| Cancelado

---

6. Status do agendamento

Cada agendamento deverá possuir um status:

- "pending" — aguardando confirmação
- "confirmed" — confirmado
- "completed" — concluído
- "cancelled" — cancelado
- "no_show" — cliente não compareceu

---

7. Notificações

Na primeira versão, o sistema poderá enviar notificações por e-mail.

Exemplos:

- Agendamento realizado.
- Agendamento confirmado.
- Agendamento cancelado.
- Lembrete do atendimento.

WhatsApp pode ser considerado uma funcionalidade futura.

8. Tecnologias sugeridas

Backend

Node.js + Express

Responsável por:

- autenticação;
- regras de negócio;
- gerenciamento dos agendamentos;
- API;
- comunicação com o banco.

Banco de dados

MongoDB

Principais coleções:

- "users"
- "clients"
- "employees"
- "services"
- "appointments"
- "blocked_times"

Frontend

Pode começar simples:

- HTML;
- CSS;
- JavaScript.

Não é necessário React para a primeira versão.

Autenticação

- Hash de senhas.
- Sessão ou JWT.
- Controle de permissões.

9. API — exemplos

Usuários

"POST /api/auth/register"

"POST /api/auth/login" - feito

"GET /api/users/me"

Serviços

"GET /api/services" - feito

"POST /api/services"

"PUT /api/services/:id"

"DELETE /api/services/:id"

Agendamentos

"GET /api/appointments" - feito

"GET /api/appointments/:id" - feito

"POST /api/appointments" 

"PUT /api/appointments/:id"

"DELETE /api/appointments/:id"

Disponibilidade

"GET /api/availability?employee=123&date=2026-08-15"

Essa rota deverá retornar somente os horários realmente disponíveis.

13. Critérios de sucesso

O sistema será considerado funcional quando:

1. Um cliente conseguir criar uma conta.
2. O administrador conseguir cadastrar um serviço.
3. O administrador conseguir cadastrar um profissional.
4. O cliente conseguir consultar horários disponíveis.
5. O cliente conseguir realizar um agendamento.
6. O sistema impedir conflitos de horário.
7. O administrador conseguir visualizar o agendamento.
8. O administrador conseguir alterar seu status.
9. O cliente conseguir cancelar conforme as regras.
10. Todas as informações permanecerem armazenadas corretamente no banco.

---

Objetivo do projeto

O sistema deve ser desenvolvido como se fosse um produto real para um pequeno negócio, e não apenas como um CRUD de portfólio.

A prioridade deve ser demonstrar:

autenticação + autorização + regras de negócio + banco de dados + API + interface + tratamento de erros + segurança.

O sistema não precisa ter dezenas de funcionalidades. É melhor entregar um produto pequeno, consistente e funcionando do início ao fim do que tentar construir um "Super App" e abandonar no meio.
